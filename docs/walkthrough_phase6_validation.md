# AutoPatch — Phase 6: Validation Agent & Tooling Walkthrough

## 1. Executive Summary

Phase 6 implements the **Validation Agent** and supporting isolated validation tooling for AutoPatch. Candidate patches generated by Phase 5 are treated as untrusted proposals. The Validation Agent executes candidate patches inside an isolated, temporary copy of the target repository, enforcing strict compile, test, and differential security scanning guarantees before any patch can be transitioned to `VALIDATED`.

The target repository is **never modified** during validation. Verification SHA-256 integrity checks prove zero bytes altered in the original repository.

---

## 2. Architecture & Pipeline

```text
Candidate Patch (PatchAttemptModel)
              │
              ▼
1. Structural Patch Validation (Unified diff regex, paths, forbidden file types)
              │
              ▼
2. Temporary Workspace (backend/tools/workspace.py)
   • Pristine copy with symlink breakout protection
   • Independent workspace teardown on completion
              │
              ▼
3. Patch Application (backend/tools/patch_applier.py)
   • Pure-Python hunk parser
   • Line offset calculation and exact block replacement
              │
              ▼
4. Syntax / Build Check (python -m compileall)
   • Controlled subprocess execution (shell=False)
              │
              ▼
5. Test Execution (backend/tools/test_runner.py)
   • python -m pytest -q
   • Timeout enforcement, stdout/stderr capture, pass/fail/skip regex parsing
              │
              ▼
6. Differential Security Re-scan (ScanningAgent.scan in sandbox)
   • Re-runs Bandit + Semgrep on temporary workspace
              │
              ▼
7. Security Comparison (Differential Matching)
   • Matches rule ID, target file, and line proximity (±15 lines)
   • Categorizes findings: resolved vs remaining vs new findings
              │
              ▼
8. Verdict & Persistence (backend/models/validation.py & backend/database/models.py)
   • Status: PASS / FAIL / ERROR / TIMEOUT
   • Persisted to validation_results table without overwriting prior attempts
   • Updates patch_attempts.status (VALIDATED or FAILED_VALIDATION)
```

## 3. Implementation Details

### Part A: Patch Generation Hardening (`backend/agents/patch_generation_agent.py`)
- Standardized coordinate calculations in `_generate_unified_diff` to resolve directly against original file sources.
- Added `_parse_diff_file_headers` to independently parse `--- a/...` and `+++ b/...` headers.
- Enforced cross-validation between `diff` headers and `LLMPatchGeneration.changes`. Mismatched files cause immediate patch rejection.

### Part B & D: Patch Applier (`backend/tools/patch_applier.py`)
- Implemented pure-Python unified diff parser and applier.
- Rejects absolute paths, UNC paths, drive letters, and directory traversal (`..`).
- Rejects test modifications (`tests/`, `test_*.py`).
- Supports hunk-based line offset adjustments and enforces trailing newline normalization.

### Part C: Controlled Test Runner (`backend/tools/test_runner.py`)
- Executes pytest using `[sys.executable, "-m", "pytest", "-q"]` with `shell=False`.
- Does not execute arbitrary LLM shell commands or scripts.
- Captures `exit_code`, `stdout`, `stderr`, `duration`, and extracts `tests_passed`, `tests_failed`, and `tests_skipped`.
- Annotates classes with `__test__ = False` to prevent pytest collection conflicts.

### Part E & F: Isolated Workspace (`backend/tools/workspace.py`)
- Context manager `TemporaryWorkspace` creates an isolated directory in `tempfile.gettempdir()`.
- Implements symlink escape prevention: verifies that resolved symlinks remain inside the repository boundary.
- Deletes the temporary workspace on exit regardless of success or failure.

### Part O: Sandbox Abstraction (`backend/tools/sandbox.py`)
- Abstract base class `SandboxExecutor`.
- `LocalWorkspaceSandboxExecutor` for isolated host execution with strict boundaries.
- `DockerSandboxExecutor` stub ready for future containerized environments.

### Part G, J, K, L, M: Validation Agent (`backend/agents/validation_agent.py`)
- Orchestrates the full validation sequence.
- Loads baseline workflow vulnerabilities to ensure existing findings in other files are not flagged as new findings introduced by the patch.
- Uses `_is_match` with `rule_id` and line proximity ($\pm 15$ lines) to distinguish between mitigated and remaining findings sharing the same CWE.

### Part H & P: Validation Models & Persistence (`backend/models/validation.py`, `backend/database/models.py`)
- Pydantic models: `ValidationStatus` (`PASS`, `FAIL`, `ERROR`, `TIMEOUT`), `SecurityComparisonResult`, `ValidationResult`.
- Database model: `ValidationResultModel` storing comprehensive execution diagnostics, stdout/stderr, security scan findings, and failure reasons.

### Part Q: HTTP API Endpoints (`backend/api/routes/validation.py`)
- `POST /api/patches/{patch_id}/validate`: Trigger validation workflow.
- `GET /api/patches/{patch_id}/validation`: Fetch latest validation record.
- `GET /api/validations/{validation_id}`: Fetch specific validation record by ID.
